# 让容器镜像学会按需读取：overlaybd 的 ARM64 查找优化

> 写给不熟悉 Linux 底层的读者。不需要内核知识，十分钟读完。

**TL;DR** overlaybd（源自阿里云、现属 containerd（CNCF）的开源项目）在 x86 上早有 AVX-512 加速的索引查找，ARM64 却一直只有标量路径。这次我们为 ARM64 补上了 NEON 与 SVE 两级 SIMD 实现，运行时按硬件能力四级自适应分派（SVE2 → SVE1 → NEON → 标量）。鲲鹏 920 真机实测：查找函数最快 **2.9 倍**（端到端收益量化中）；所有实现与标量参考**逐位一致**；x86_64 路径与磁盘格式均零改动。

---

## 一、容器镜像为什么"重"

一个典型的容器镜像是分层的文件包：操作系统库 + 运行时 + 你的应用，压缩后动辄几百 MB 到几个 GB。传统启动方式是"整本搬回家"：

1. 从镜像仓库下载完整镜像（网络传输）
2. 解压展开到本地磁盘——体积可能翻倍：几百 MB 的压缩包摊成几 GB
3. 然后容器才能启动

镜像越大，等待随之拉长——冷启动慢，是容器平台的经典痛点。

overlaybd 把"搬回家"改成"按需借"：将镜像抽象成一块**云上的虚拟硬盘**（块设备），容器启动时只挂载——把这块"盘"接进系统——不下载，读到哪块才从远端仓库取哪块。数据从哪来？镜像数据仍存放在远端仓库，overlaybd 内置本地缓存，读过的块会留在本地，热点数据不必每次跨网络。这和流媒体把"下载整部电影"变成"播到哪缓冲到哪"，是同一个思想。

## 二、按需读取的代价：每次读都要"查账"

"按需借"不是免费的。容器读一个 4KB 数据块时，overlaybd 必须瞬间回答：

> 这个块，在镜像的哪一层、哪个文件、哪个偏移？

回答这个问题靠**索引**。overlaybd 用 LSMT（Log-Structured Merge Tree，日志结构合并树）组织镜像——可以想象成一本"分层账本"：下层是只读的镜像层（历史账页，不可涂改），上层是可写层（新账页）。读数据时从上往下翻：最上层有就用上层的，没有就往下层找。

索引本体是一棵**线性化 B+ 树**——按 key 分层的有序索引。读数据时沿树从根往下走，每一层都在一个节点里做一次"内部查找"：

> 在 16 个已排序的 key 里，定位目标该走哪个分支——返回一个 0～16 的位置。

这个函数只有几行代码，却是热路径中的热路径——每次块读都要执行。overlaybd 在 x86 上把索引组织成线性化 B+ 树、并用 AVX-512 加速节点内查找，相比老的二分查找快 10 倍以上。ARM64 侧则只有标量 fallback：我们实测 gcc 12 -O3 的自动向量化对这个循环无能为力（向量化报告输出为零——它带数据相关的比较与归约）。

本次优化的范围因此非常小：**只给 ARM64 补上查找函数的 SIMD 实现。**但要理解它为什么值得做、为什么安全，得先看清这棵树长什么样、key 到底是什么。

## 三、key 是什么：解剖 overlaybd 的索引

把 overlaybd 的卷看成一条很长的磁盘：以 512 字节扇区为单位编号，容器读数据就是读其中某些扇区区间。索引要回答的问题因此非常具体：

> 第 X 个扇区开始的这段数据，现在存在哪里？

**key 就是扇区编号（LBA）。**索引的基本条目叫"段"（segment，128 位/条）：一个段声明"卷里从第 X 扇区开始的 N 个扇区，内容在数据文件（blob）的第 Y 扇区"。所有段互不重叠、按起始扇区排序——上层可写层新写的数据，本质上是插入新段、覆盖旧段。所以索引长成"按 key 分层的有序索引"：线性化的意思是整棵树摊平存成一段连续内存——内节点固定 64 字节（一条 cache line），装 16 个 32 位 key——每条 key 宽 4 字节，按 512 字节扇区算，最大可寻址约 2TB 的卷；更大的卷改用 8 个 64 位 key，key 宽度翻倍、个数减半，节点仍是一条 cache line。两种树不是人工配置的：打开卷、合并各层索引时自动选择——卷小于 2TB **且**段数少于约 3.9 亿用 u32，任一越界自动切 u64（树更高、扇出 9，查找代码对两者完全无感）。key 升序，第 i 个 key 大于它、小于第 i+1 个 key 的所有段挂在第 i 个分支下。查找就是从根往下走：每层一次查找函数（inner_search）定位分支，走到叶子就命中了段。

树很矮：u32 树每层"16 key → 17 分支"，七层就能容纳约 3.9 亿个段，典型镜像只需三到五层。这意味着一次块读只需三到五次 inner_search，每次恰好碰一条 cache line——没有指针跳转，没有随机访存。

把一次真实的读请求从头走一遍，四个角色——key、段、B+ 树、blob——就在这一条路径上（数字为示意，节点内 16 个 key 图中各画 3 个）：

```text
容器读请求：第 1000 扇区起，读 8 个扇区
  │
  ▼ ①树下行（每层一次查找函数，看一个 64 字节节点）
  根节点   [ 400 | 800 | 1200 | … ]      ← 16 个 key，图中画 3 个
  │        1000 落在 800~1200 → 走该分支
  ▼
  内节点   [ 900 | 990 | 1050 | … ]
  │        1000 落在 990~1050
  ▼
  叶子 · 段数组（按 key 排序）
  [900|len 90] [990|len 20] [1050|len 40]
                 ▲ ②命中段：990 ≤ 1000 < 1050
                 │  段 = key 990 · len 20 · moffset 8800
                 ▼ ③按 moffset 去 blob 取数
  blob（镜像数据文件）的扇区：
  … 8800 | 8810 8812 8814 8816 …        ← 实读 8800+(1000−990)=8810 起 8 扇区
                ▲██████████▲
  ④数据沿原路返回容器
```

一次读 = 两三层树下行（每层一条 cache line）+ 一次段命中 + 一次 blob 定位。索引的全部工作，就是把"第 X 扇区在哪"变成这条固定几步的路径。

## 四、为什么要 B+ 树：一笔内存账

大镜像的索引动辄上百万个段，一百万个段排成有序数组约 16MB——远大于 CPU 缓存。最直接的查找是二分：每次比较排除一半，20 步就能定位，比较次数少得不能再少。但瓶颈从来不在"比较"上：CPU 做一次比较不到 1 纳秒，等一次内存却要约 100 纳秒，差着百倍；而二分查找每一步看哪个位置由上一步的结果决定——CPU 无法提前准备，只能干等，20 步里大多是等待。**这就是"内存墙"：算得快不算本事，喂得上才算。**

打个比方：在 1000 页的字典里查一个词，每翻一页都要等图书管理员从库房取来——翻 20 页，等 20 次。B+ 树的原理，是让管理员把目录卡片放到手边：

1. **分组与路标**：与其在 100 万个段里直接找，先看 16 个"路标"（根节点）判断该去哪个大区，再层层往下。每层缩小 17 倍，百万个段也只需五层左右。
2. **路标足够小**：每层只看一个 64 字节节点，树的顶端几层可以长期住在 CPU 缓存里，只有最后一步才真正去摸大数组（叶子）。
3. **线性化消灭指针**：普通内存版 B+ 树节点之间靠指针相连——下一个节点在哪仍由节点内容决定，还是"猜地址"。overlaybd 把整棵树按层摊平进一个连续数组，孩子在数组中的位置由父节点位置直接算出（扇出 17），不存指针。地址可预测，硬件就能提前取数。

三招下来，20 次不可预测的内存等待变成 3～5 次大多命中缓存的短查。x86 实测（整棵索引每秒可完成的查找次数，越大越好）：

| 方案 | 1k 段 | 100k 段 | 1M 段 |
|---|---|---|---|
| 有序数组 + 二分（std::lower_bound） | 18.3 M/s | 8.6 M/s | 5.6 M/s |
| 线性化 B+ 树（标量位运算） | 42.2 M/s | 21.8 M/s | 15.2 M/s |
| 线性化 B+ 树 + AVX-512 | 220 M/s | 108 M/s | 57.4 M/s |

**收益拆账**：B+ 树结构本身带来 2～3 倍（少等内存），节点内 SIMD 再叠 3～5 倍（一次比 16 个），合计 10 倍以上；段数越大越稳——数组越大，二分查找的缓存等待越痛。

树形红利到此讲完。下一节进入节点内部：16 个 key 怎么在几纳秒内定位——那里才是 SIMD 的舞台。

## 五、B+ 树为什么和 SIMD 是天作之合

在 16 个已排序的 key 里找位置，教科书答案是二分查找：四步比较就能定位。但每一步都依赖上一步的结果——比较无法并行，分支预测屡屡落空，访存地址跳来跳去。

线性化 B+ 树给了另一个答案。16 个 key 恰好一条 cache line，可以整体装进向量寄存器：

```
__m512i vx     = _mm512_set1_epi32(x);     // 目标值广播到 16 个"车道"
__m512i data   = _mm512_load_si512(base);  // 一条 cache line：16 个 key
__mmask16 mask = _mm512_cmp_epu32_mask(vx, data, _MM_CMPINT_GE); // 16 次比较，一次完成
return __builtin_popcount(mask);           // 有几个 key ≤ x，位置就是几
```

（这是 overlaybd x86 路径的真实代码。）16 次比较并行完成，结果压成一个 16 位掩码；"数掩码里 1 的个数"（popcount）直接给出位置——无分支、单次遍历、一次访存。在 16 个元素的规模下，这套"宽指令 + 位运算"的组合，比"省几次比较却处处串行"的二分快得多——上一节的结构红利之上，又叠上了第二层：内核红利。

也正因为这个内核是"批量比较 → 归约成位置"的数据依赖结构，编译器的自动向量化帮不上忙。ARM64 上同样的机制要靠手写 NEON/SVE 重新实现一遍——这正是本次优化的全部内容。

## 六、五分钟 SIMD 入门

（熟悉 SIMD/SVE 的读者可以直接跳到第七节。）

SIMD（Single Instruction, Multiple Data，单指令多数据）的朴素理解是：**一条指令，同时处理一批数据**。就像灌装流水线：逐瓶灌是循环，一次灌一排才是 SIMD。

**NEON：固定 4 车道。** 所有 ARM64 CPU 都自带 NEON——128 位向量寄存器，一次装 4 个 32 位数。查找函数里"逐个比较 16 个 key"的循环，可以变成"一次比较 4 个、比四轮"。

**SVE：车道数由芯片决定。** SVE（Scalable Vector Extension，可伸缩向量扩展）更进一步：向量寄存器宽度不固定，128 位到 2048 位，由芯片设计者决定。代码写成"向量长度无关"（VL-agnostic）：程序运行时问硬件"你多宽"，然后自动吃满。鲲鹏 920 的向量长度是 256 位——一条指令同时比较 8 个 key。同一份代码放到 512 位的机器上，不用改一行就自动吃满 16 个。

**SVE1 与 SVE2。** SVE2 是 SVE 的第二代指令集扩展。对本文的查找函数（比较 + 计数）而言，SVE1 指令集是 SVE2 的子集——同一份 SVE1 编译产物可以直接跑在 SVE2 硬件上，差别只在硬件能提供多宽的向量。

## 七、先在真机上证明值得做

动手改产品代码之前，我们先在鲲鹏 920（7280Z，256 位 SVE1，openEuler 24.03）上给三种实现——标量 / NEON / SVE——各写了一个微基准，量同一次"16 个 key 里找位置"的耗时：

| 查找函数 | 标量 | NEON（128 位） | SVE（256 位） |
|---|---|---|---|
| u32 / 16 key | 23.6 ns | 12.0 ns（**2.0x**） | 8.1 ns（**2.9x**） |
| u64 / 8 key | 15.9 ns | 13.1 ns（1.2x） | 8.3 ns（**1.9x**） |

两个值得注意的细节：

- **加速在工作集从 32KB（L1 量级）到 256MB（内存量级）的四档规模下稳定成立**——不是只对"恰好都在缓存里"的数据快。
- u64 这一组 NEON 只拿到 1.2 倍：128 位寄存器一次只装 2 个 64 位数，把一排比较结果合并成一个位置的收尾开销（归约）吃掉了大半收益；SVE 256 位一次装 4 个，回到 1.9 倍。**向量越宽，优势越大**——这也解释了为什么值得为 SVE 单独写一版。

### 把节点内的算术摊开看

一层 B+ 树的比较，就是"一个节点内的全部 key"的比较。各档位一次 SIMD 能覆盖多少、一层要比几轮：

| 实现档位 | 一次 SIMD 比较覆盖 | u32 节点（16 key） | u64 节点（8 key） |
|---|---|---|---|
| AVX-512（x86 参照） | 16 个 u32 / 8 个 u64 | 1 轮 | 1 轮 |
| SVE 256 位（鲲鹏 920） | 8 个 u32 / 4 个 u64 | **2 轮** | **2 轮** |
| NEON 128 位 | 4 个 u32 / 2 个 u64 | 4 轮 | 4 轮 |
| 标量 | 1 个 | 16 轮 | 8 轮 |

读法：鲲鹏 920 向量长 256 位，一条 SVE 比较指令同时处理 8 个 u32（或 4 个 u64），16 个 key 的节点两轮走完。SVE 代码写成向量长度无关——循环步长就是硬件报告的向量宽度，同一份代码放到 512 位机器自动变成一轮。每轮比较之后还要一步归约（把每条车道的是/否合并成位置），所以上表的轮数同时决定了比较与归约的开销：SVE 两轮对 NEON 四轮，正是 2.9x 拉开 2.0x 的主要来源；x86 的 AVX-512 一轮吃下整个节点，是它查找吞吐更高的原因之一。

## 八、怎么让它安全落地：五个工程决策

查找快了近 3 倍只是开始。overlaybd 要跑在所有 ARM64 机器上——从只有 NEON 的老芯片到向量更宽的 SVE2 服务器——一个 SIMD 实现要落地，真正的工作在工程侧。

### 决策 1：运行时"自动挡"——四级档位自适应

同一份二进制要适配所有机器，编译期选边是行不通的。我们采用运行时分派：程序启动建索引时，向 Linux 内核询问 CPU 的能力位（HWCAP 机制：内核用两张位图 HWCAP / HWCAP2 向程序通报 CPU 能力——相当于开机时问一句操作系统"这台机器支持什么"），然后按阶梯选择最高可用档位：

| 档位 | 探测方式 | 示例硬件 |
|---|---|---|
| SVE2 | HWCAP_SVE + HWCAP2_SVE2 | Neoverse V2 / Grace、Graviton4 |
| SVE1 | HWCAP_SVE | 鲲鹏 920（256 位）、Graviton3 |
| NEON | aarch64 架构保证，免检 | 所有 ARM64 |
| 标量 | 无需探测（其余档位均不可用时） | 语义参考 / 降级构建 |

选择结果写进日志（`tier=SVE1, vl_bytes=32`，32 字节即 256 位）。出性能问题时，先查日志确认当前在哪一档。

### 决策 2：SVE 代码单独编译，并禁用 SVE2 指令

SVE 代码放进一个独立的编译单元，编译选项固定 `-march=armv8.2-a+sve`，**明确禁用 `+sve2`**。

为什么这么强硬？鲲鹏 920 是 SVE1 机器：它没有 SVE2 指令。只要编译选项含 `+sve2`，编译器就有权生成 SVE2 指令（自动向量化可能悄悄用上），而程序一旦执行到 SVE2 指令，CPU 触发非法指令异常——SIGILL，进程直接崩溃。这是我们在真机上实测确认过的坑（HWCAP2_SVE2=0，即这台机器上报自己不支持 SVE2），硬规则连同原因写进了代码注释。

同样出于跨硬件考虑，我们拒绝了 `-msve-vector-bits=256` 这种定长编译——它把代码绑死在 256 位上。VL-agnostic 写法让一份编译产物覆盖 128～2048 位（规范允许的全部宽度），实测覆盖 256 位。

### 决策 3：构建期探测，老工具链自动降级

SVE 要较新的编译器（GCC 10 起）才提供 `arm_sve.h`。而 overlaybd 的发布矩阵里还有 centos7 + gcc7 的组合。解决办法是 CMake 构建探针（编译选项检测 + 探针文件双检）：探测失败就跳过 SVE 编译单元，NEON/标量路径照常，**构建不因工具链缺少 SVE 支持而失败**。此外还留了手动逃生门：`OVERLAYBD_DISABLE_SVE=1` 一键回到旧路径。

### 决策 4：对拍——把"算错"变成机器可查

SIMD 优化最大的风险不是"没变快"，而是"算错了但多数时候看起来对"。我们把验证做成了机械检查：随机生成的索引数据，外加边界情况——目标在开头/结尾、目标落在两个 key 之间的空隙、目标恰好等于某个 key、节点 key 数不满需补位（padded leaf）——每个 SIMD 实现与标量参考**逐位比对**。鲲鹏真机 35/35 单测通过，零失配。

### 决策 5：只动查找函数，别的一概不碰

x86 路径原样保留（AVX-512 检测逻辑不动）；磁盘格式不变；不引入新依赖（`arm_sve.h` 随编译器提供）；所有实现共用同一函数接口（模板签名），改动集中在一个选择点。回滚 = 撤销（revert）一个提交。

## 九、结果与诚实的边界

- **查找函数：1.2～2.9 倍**（视数据宽度与档位；u32 这组为 2.0～2.9 倍。鲲鹏 920 真机，数据见附录）
- **端到端收益：量化进行中。** 查找加速不等于端到端等比提升——除查找外，一次读还要经过压缩、网络传输、操作系统的磁盘读写等环节，各有开销。我们正在用磁盘基准工具 fio 做前后对比：先测缓存热读的 4K 随机读，以控制变量隔离查找开销，冷读路径随后补测，数字出来后更新本文。
- **档位可观测：** 每次建索引时日志报告档位与向量长度。
- **SVE2 档：** 尚未有真机验证。兼容性有架构保证（SVE1 指令集是 SVE2 的子集，SVE1 编译产物可直接运行），但正确性仍需拿到 SVE2 硬件（如 Graviton4、Neoverse V2）后冒烟验证。

## 十、可复用的三条经验

1. **新指令集落地老发行版的标准姿势**：编译隔离让老工具链能构建，运行时分派让新硬件吃满，构建期探测让两者互不阻塞。三者合起来，一份代码从 centos7 + gcc7 一路跑到向量更宽的 SVE2 服务器。
2. **微基准先行**：先花半天在真机上证明查找值得优化，再决定是否投入端到端改造——顺序反了容易做完才发现收益被稀释。
3. **对拍是 SIMD 正确性的最低成本保险**：所有实现与标量参考逐位比对，把"看起来对"升级成"机械可证"。

## 附录 A：实测环境与参照数据

鲲鹏 920 7280Z（256 位 SVE1，openEuler 24.03，gcc 12.3），单线程耗时；节点 = 16×u32 或 8×u64 key，恰一条 cache line。收益在工作集 32KB（L1 量级）→ 256MB（内存量级）四档规模下稳定成立。
